# Задание 4. Проектирование продажи ОСАГО

1. Требуется ли ему своё хранилище данных?
   PostgreSQL: Да. Нужен как минимум для:
   1.1. Кореляции между sessionid и insurerReauestId
   1.2. Состояние работы приложения(автомата) по каждому страховщику
   1.3. Состояние retry, deadline 
   1.4. Журналы публикации в outbox
   Redis: Кэш ответов и сессий

2. Какой API он предоставляет core-app?
   core-app публикует запрос на предоставление информации
   osago-aggregator обрабатывает и запускает fan-out процесс опроса к страховщикам, по мере получения ответов публикует в два топика.
   1 топик частичные данны 2-ой полная сборка чтобы не зависеть от самого медленного. Здесь это не является антипаттерном так как по своей сути запрос не является командой которую core-app ждет немедленного выполнения а получает порционно по мере готовности что похоже на event-driven подход
   core-app подписывается на топики получая данные по sessionId
   REST API нужен для легковесных запросов
3. Определите средство интеграции между сервисами core-app и osago-aggregator.
   Как и говорилось в предыдущем пункте Event streming подход: команды(запросы на выполнение) и события.
   Также используется transactional outbox в обоих сервисах для атомарности операций
4. Подумайте над API для веб-приложения в core-app.
   для REST это создание сессии возвращая sessionId и получение текущего сосотояния. 
   Для режима онлайн получения данных (требование отображать сразу) об оформления страховки можно использовать однонаправленый протокол SSE
5. Определите средство интеграции между веб-приложением и core-app. Если будете использовать средство, отличное от REST, отразите интеграцию новой стрелкой.
   REST + SSE
6. В зависимости от выбранных средств интеграции подумайте, требуется ли где-то применение паттернов отказоустойчивости:
   * Rate Limiting - для osago-aggregator для каждой страховой компании свой лимит на количество запросов,
   * Circuit Breaker - также для osago-aggregator можно ввести чтобы при 500 ошибках временно разрывалась связь. Можно брать данные из кеша,
   * Retry применить экспоненциальную задержку после нескольких попыток перейти к Circuit Breaker,
   * Timeout каждый вызов имеет свой timeout + deadline=60s. Соответственно если страховая не ответила, то возвращаем либо частичный ответ, переходим далее.
Отобразите применение паттернов на схеме с помощью обозначений из этой библиотеки.
7. Примите во внимание, что сервисы задеплоены в нескольких экземплярах. Подумайте, зависит ли ваше решение от этого.
   Kafka: партицирование по sessionId. Одну сессию потребляет одна реплика
   SSE: core-app держит SSE. При горизонтальном масштабировании (на схеме 2 инстанса) FE будет попадать на одну из реплик, а состояние хранится в Redis и core-db.
   Osago-aggregator: stateless сервисы котрые подхватывают задачи из топика однако остается проблема что каждая реплика имеет свой rate limiter и значит могут умножатся лимиты, т.е. будут пропускаться правила ограничения, для этих целей можно использовать журнал скользящего окан в Redis
   Outbox: использовать локер для того чтобы только одна реплика могла изменять запись в outbox
