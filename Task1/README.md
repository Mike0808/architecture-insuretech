## 1. Определите стратегию масштабирования и отказоустойчивости.

[Рассмотрите вертикальное и горизонтальное масштабирование для вашей системы. Оцените, какая стратегия будет эффективнее. Требуется ли использование дополнительных зон безопасности?]()
Допустимое время простоя в год (D_год):
Год = 365 дней = 365 x 24 x 60 = 525 600 минут
Доступность приложения (A) = 99,9%
D_год = (1 − 0.999) x 525 600 = 0.001 x 525600 = 525мин / 60 = 8ч 45 мин 

Инцидентов удовлетворяющих RTO = 45 мин за год может произойти максимум 11 полных инцидентов: Nинц = 525,6/45 = 11,68 шт.
Согласованное время обслуживания(T): 
T = (100 * D) / 100 - A = 100 * 45 / 100 - 99.9 = 45 000 мин ~ 750ч на 1 инцидент
Соответственно на максимальное возможное количесвто инцидентов в год 11 вычисляем годовое согласованное время: 750 * 11 = 8250ч
Проверяем
A = (8250 - 8 / 8250) * 100 = 99,89% ~ 99.9%
В рамкха улучшения масштабированности, отказоустойчивости и доступности необходимо применить следующие практики:
1. Для Stateless приложений использовать HPA. Нет привязанности к состоянию приложения. Эластичность, рекация на RPS и очереди. 
   Применимо к: client-info, ins-product-aggregator, ins-comp-settlement
  – web: по RPS/latency,
  – core-app/client-info: CPU/RAM и RPS,
  – ins-product-aggregator: по внешним таймерам/очередям (KEDA).
1. Для Statefull применимо VPA. Не нужно думать о синхронизации состояния или балансировке сессий. Минимум накладных расходов. Меньше сетевых переходов, кешей, транзакций. Подходит к: core-app
   Примечание: При росте нагрузке необходимо применить eventualy-split и перейти на HPA для core-app на следующие домены: 
   a. policy-service - Траховые продукты
   b. quote-service - Расчет тарифов и страховок
   c. document-service - генерация pdf страховки
   d. user-auth-service - иденификация клиентов
2. Для масштабирования, отказоустойчивости и доступности применить разделение на нескользо регионов и зон доступности для сервисов и базы данных в AZ-a Primary AZ-b Replica плюс обвязка для patroni. Соответственно для каждого региона используется отдельный кластер внутри которых кластер кубернетеса один на несколько зон. В каждой зоне должен разворачиваться как минимум 1 pod с сервисом. Применить Cluster Autoscaler
3. Для отказоустойчиваости необходимо применить бэкапирование в multizone S3 объектное хранилище

## 2. Если приняли решение деплоить приложение в нескольких зонах безопасности, то продумайте и отразите на схеме следующие вопросы: 

### a. Проработайте конфигурацию развёртывания приложения в Kubernetes. 
core-app - 2 реплики. По 1 реплике на каждую AZ 
web, client-info, ins-product-aggregator,ins-comp-settlement - 1-10 реплик с равномерным распределением по зонам 

### b. Спланируйте балансировку нагрузки. 
Между регионами исользовать глобальный балансировщик для геораспределения GSLB
Kubernetes: Внутри региона в расширенном кластере kubernetes на несколько AZ балансировка происходит через Ingress контроллер kube-proxy будет искать node в тойже AZ из которой пришел запрос. Напрмер после балансировки GSLB приходит в регион R1 на web UI Node AZ-a тогда запросы от web UI AZ-a попадут на тот же AZ-a на backend core-app
Для PostgreSQL с patroni разворачивается свой балансировщик который настраивается что команды проходят в, например AZ-a где установлен primary а запросы на чтение могут проходить в AZ-b.
### c. Определите наиболее подходящую фейловер-стратегию.
Она должна отвечать заданным требованиям отказоустойчивости. Отразите её на схеме на уровне взаимодействия клиента с приложением.
Для данного архитектурного решения распределенного по нескольки регионам и AZ использовать active-active фейловер-стратегию с асинхронной репликацие для PostgreSQL  
### d. Определите конфигурацию базы данных. 
Учитывая требования RTO и RPO, спроектируйте конфигурацию базы данных: определите, как вы будете обеспечивать репликацию данных и их резервное копирование. Если будете использовать конкретный фреймворк конфигурации кластера БД, отразите его на схеме.
