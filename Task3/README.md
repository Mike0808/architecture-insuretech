# Задание 3. Переход на Event-Driven архитектуру
## 1. Проблемы и риски текущей модели
1. Синхронная фан-аут агрегация (ins‑product‑aggregator -> 5 страховых):

   * При добавлении ещё 5 провайдеров время ответа и вариативность латентности вырастут кратно;
   * Провайдеры с долгим ответом блокируют общий ответ при формировании общего аггрегированного списка;
   * Рост сетевых соединений и TLS‑handshake при пиках.
2. Пулл‑репликации в core‑app и ins‑comp‑settlement:

   * 15‑мин и суточное окно создают устаревшие каталоги (несогласованность тарифов);
   * плановые запросы создают нагрузку в часы запуска;
   * синхронные зависимости повышают MTTR при деградации агрегатора/провайдеров.
3. Суточный REST‑пулл полисов (ins‑comp‑settlement -> core‑app):

   * риск пропуска данных или появление дубликатов при сетевых сбоях;
   * тяжёлые «выгрузки за день» бьют в БД core‑app;
   * нет событийной трассировки (кто, когда, какой полис).
4. Отсутствие backpressure и rate limiting между BFF/агрегатором/провайдерами:

   * один партнёр способен «съесть» ресурсы (из условия);
   * нет «watermark»/ограничителей по каждому внешнему провайдеру.
5. Ошибки интеграции и ретраи:

   * нет DLQ/parking‑lot для сообщений/запросов с ошибками;
   * ретраи из cron -> повторные оформления/рассинхронизация.
6. Наблюдаемость и SLO:

   * нет сквозных trace‑id;
   * нет чёткой сегментации p95 по провайдерам;
   * «немые» ошибки приводят к позднему обнаружению инцидентов.
7. Эволюция схем:

   * ручное версионирование контрактов;
   * отсутствие Schema Registry повышает риск несовместимостей при добавлении новых страховщиков.
8. Риск «горячих» точек в БД:

   * суточные батчи + 15‑мин выгрузки -> локальные пики I/O/locks;
   * отсутствие идемпотентности запросов оформления (потенциально).

## 2. Принципы обновления (не меняя функциональную декомпозицию)

### 2.1  Перевести каталог продуктов/тарифов с pull‑модели на event‑streaming (pub/sub):

  * ins‑product‑aggregator нормализует ответы провайдеров и публикует события product.upsert, tariff.upsert, insurer.status в Kafka;
  * core‑app и ins‑comp‑settlement подписываются и поддерживают локальные read‑модели (кеш/таблицы) в актуальном состоянии;
  * для онлайн‑поиска/котировок оставить синхронный API с параллельным fan‑out, но с жёсткими дедлайнами, частичным ответом и fallback к кэшу.

### 2.2 Полисы (оформление/отмена) — тоже события: policy.issued, policy.canceled (источник: core‑app). Settlement подписывается и перестаёт делать суточный pull; для сверки оставить легковесный REST‑endpoint
### 2.3 Везде, где данные меняются в БД, применять Transactional Outbox:
  * запись доменной сущности + outbox‑записи в одной транзакции;
  * доставку в Kafka выполняет outbox‑relay -> гарантия at‑least‑once и упорядочивание по aggregate‑key.
### 2.4 Ввести Schema Registry (Avro/Protobuf/JSON‑Schema) и эволюцию схем (backward‑compatible).
### 2.5 Внешние страховщики — через bulkhead + per‑provider rate‑limits + circuit‑breaker; запросы агрегатора параллельные, с deadline и hedging (дублирование на t+X мс при хвостах).
### 2.6 Добавить DLQ/parking‑lot для сообщений, которые не удалось обработать после N ретраев.
### 2.7 Наблюдаемость: trace‑id сквозь BFF -> агрегатор -> провайдер; SLO дашборды p50/95/99 per insurer, лаг потребителей, размеры топиков, количество отклонённых квот.


## 3. Где именно вводим Event‑Streaming

* ins‑product‑aggregator -> Kafka: события каталога и статусов провайдеров.
* core‑app -> Kafka: события жизненного цикла полиса (policy.*).
* ins‑comp‑settlement <- Kafka: потребляет policy.* и tariff.*; формирует реестры без суточного REST‑pull.
* core‑app / ins‑comp‑settlement поддерживают локальные проекции (Redis) из потоков событий.

## 4. Transactional Outbox — применять?

Да, обязательно:
* в ins‑product‑aggregator (фиксация нормализованных тарифов -> outbox -> Kafka);
* в core‑app (оформление/отмена полисов -> outbox -> Kafka);
* в ins‑comp‑settlement (изменения статуса взаиморасчётов -> опционально публиковать settlement.status).
  Реализация: Outbox‑таблица + ретранслятор ключ — insurer_id/product_id или policy_id.
